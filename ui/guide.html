Your complete presentation script

Follow the actions in order. Each step tells you what to do, what to show, and what to say. Rehearse once before your examiner arrives.

Two operating systems, on one physical laptop. Windows runs the gateway, Modbus controller simulator, database, and protected dashboard. Your existing Ubuntu VM runs the operator application and controlled tests. This is a two-endpoint VM demonstration; it is not two separate physical computers.

First understand the project

A water-control system accepts instructions such as “set chlorine to 1.80 ppm” or “open the valve to 70%.” A bad instruction could change the process. WaterGuard checks every write before the controller receives it, blocks unacceptable requests, and protects the resulting evidence.

Problem: native Modbus TCP does not itself provide WaterGuard's identity, command-signature, replay, or process-policy checks.

Objectives: authenticate sources and commands; reject repeated or stale requests; protect read-only registers; enforce configured ranges; capture traffic; store protected evidence; show real state and measured outcomes.

Design: the client sends a JSON command through WCP to Windows port 6000. The gateway validates it and forwards accepted writes as Modbus TCP to the localhost-only controller on port 5502. Raw untrusted Modbus on port 1502 is rejected. The dashboard serves HTTPS on port 8443. The Ubuntu operator page is local HTTP on port 8080; its backend signs commands.

Honest wording: “This is a prototype water-control security gateway demonstrated against a software controller.” Do not describe the animated tank as a physical sensor or claim a universal zero false-positive rate.

15 · Show where the validation logic lives

ACTION: Windows → Security decisions → select the forged-HMAC row → Validation trace. Then select an accepted row to compare.

SHOW: Schema, source, freshness, HMAC, nonce, access, safety, forwarding. For the forged command, later stages are SKIPPED, not passed. Show its received JSON and event ID.

SAY: “This is the actual trace stored by the gateway for this event. It uses fail-fast validation: the first failed check determines the reason and later checks are not executed.”

The nonce cache is in memory and resets on gateway restart. Timestamp freshness still applies. This is not persistent replay protection across restarts.

16 · Explain command HMAC in words you understand

ACTION: Select an accepted event → Encryption proof → Step 1. Expand its readable command and canonical command bytes.

SHOW: The five signed fields client_id, register, value, timestamp, nonce, followed by the HMAC field.

SAY: “HMAC-SHA256 is a secret-key authenticity check. Both sides calculate it over exactly the same five command fields. The gateway compares the tag in constant time. A 64-character hex tag can have the correct format and still be cryptographically wrong.”

The command nonce is 16 random bytes written as 32 hex characters. Hex is a readable way to encode bytes; it is not encryption. Freshness uses abs(current_time - timestamp) ≤ 5 seconds, so zero, subsecond differences, and small future timestamps can also pass.

FILES: client/legit_hmi_client.py, shared/wcp_protocol.py, and shared/crypto_utils.py.

17 · Show the complete encryption and decryption proof

ACTION: On Windows open https://localhost:8443/ → Security decisions → select an event → Encryption proof. Work down the six numbered steps.

SHOW: Received command and gateway decision; canonical readable evidence JSON and its bytes; SHA-256; evidence HMAC; AES nonce; stored ciphertext and GCM tag; decryption and all verification PASS results.

SAY: “The gateway builds an evidence record containing the command, source, time, checks, and decision. It hashes the exact canonical bytes with SHA-256, authenticates that hash with a separate HMAC key, and encrypts the evidence using AES-256-GCM.”

SAY: “AES uses a 32-byte key, a fresh random 12-byte nonce, and a 16-byte authentication tag. This AES nonce is separate from the command's replay nonce. The key is not printed.”

SAY: “The readable evidence shown here has been decrypted from the stored ciphertext and checked. The application does not keep a separate plaintext evidence file. This view reconstructs the exact bytes used before encryption.”

SAY: “To trust a record, decryption must succeed, the recomputed hash and HMAC must match, and all duplicated clear database columns must match the protected record.”

FILES: gateway/evidence_store.py → record_event(), decrypt_and_verify_event(); shared/crypto_utils.py → aes_gcm_encrypt(), aes_gcm_decrypt(); gateway/evidence_proof.py → show_proof().

Be exact: AES encrypts stored evidence, not the WCP transport. Command HMAC provides authenticity/integrity, not secrecy. The dashboard uses HTTPS; the WCP and localhost Modbus links are not encrypted.

OPTIONAL DATABASE TOOL: If DB Browser for SQLite is already installed: Windows Start → type DB Browser for SQLite → Open Database → select the displayed data\waterguard_evidence.db path → Browse Data → choose security_events. Or Execute SQL → paste the query below → click Execute.

SELECT id, event_id, ts, client_id, peer_ip,
       decision, reason, stage, payload_hash, hash_hmac,
       lower(hex(aes_nonce)) AS aes_nonce_hex,
       lower(hex(encrypted_payload)) AS ciphertext_hex
FROM security_events
ORDER BY id DESC
LIMIT 20;

19 · Prove that changing ciphertext is detected

ACTION: Windows → Encryption proof → scroll to One-bit tamper demonstration → click Demonstrate tampering on a copy.

SHOW: Copy before INTACT, copy after TAMPERED, one changed bit, original unchanged YES, original intact YES, and the copy's database path.

If something goes wrong

  • VM crashes: the new app does not change VirtualBox hardware or adapters. Keep your last working VM setup and solve VM boot separately before opening this app.
  • Windows unreachable: check that Windows WaterGuard is running; confirm the current Wi-Fi IP; verify the bridged network and firewall address; leave port 5502 closed.
  • source_spoofing: Windows expects a different Ubuntu IP. Stop the launcher, correct the Ubuntu address, start again, reconnect.
  • invalid_hmac for normal input: use the client ZIP exported from the currently running Windows project. Do not transfer evidence keys or change all three keys to fix a command-key mismatch.
  • replay_attack for a new command: synchronize clocks. Ubuntu: timedatectl status, then sudo timedatectl set-ntp true. Windows: Settings → Time & language → Date & time → Set time automatically → Sync now. Reconnect afterward.
  • Port already in use: stop the old project and old operator service. Close the previous launcher before starting another copy.
  • Capture failure: verify Wireshark/Npcap and select the actual Wi-Fi + loopback interfaces. Do not disable capture silently and claim traffic proof.
  • Local access required: open the protected proof on Windows at https://localhost:8443/, not the Wi-Fi address from Ubuntu. This restriction intentionally keeps decrypted evidence local.
  • Chlorine naturally changes: the original simulator slowly decays chlorine. Compare the request, accepted event, and prompt telemetry; use the stable valve value for an especially clear state-change proof.
  • Old database missing: the new folder starts with a new database. Your old folder is unchanged. To inspect old evidence, use that folder with its original evidence keys. Do not overwrite keys or copy only a live WAL database's .db file.

Viva answers you can explain

QuestionAccurate answer
Is AES encrypting the command on the network?No. WCP commands use HMAC authenticity; AES-GCM protects stored detailed evidence. HTTPS protects dashboard transport.
Why two nonces?The command nonce identifies a request for replay protection. The separate AES nonce makes each evidence encryption distinct under the same key.
Can an authenticated client still be dangerous?Yes. Valid HMAC does not prove a setpoint is acceptable. Register access and configured safety bounds are independent checks.
Where does the source IP come from?From the accepted TCP socket's peer address. The gateway compares it to the client-ID/IP registry on Windows.
Does Modbus protect itself?This prototype's native Modbus controller does not authenticate writes. The inline gateway and loopback-only controller deployment provide the boundary.
Why HMAC plus AES-GCM?AES-GCM authenticates encrypted content. A separate HMAC authenticates the stored SHA-256 hash using another key. The hash is a convenient evidence fingerprint.
Do your checks prevent all attacks?No. This prototype covers the implemented command and evidence threat model. It does not provide production-grade DoS resistance, persistent nonce history, immutable storage, or protection after every secret key is stolen.
Is your GUI proof fabricated?No. The trace is written while checks execute; the evidence view reads the stored SQLite BLOB, decrypts it, recomputes verification values, and checks duplicated metadata.
What does a green ALLOW prove?The gateway accepted the request and received a successful controller write acknowledgement. The telemetry then shows current registers. It is not a claim about a physical plant.
What does TAMPERED prove?The record failed one or more integrity checks. A changed ciphertext can fail GCM; changed duplicated metadata is detected by cross-checking against the protected JSON.
